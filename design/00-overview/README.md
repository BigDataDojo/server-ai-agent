# 全体像

## 目的

研究室のインフラは便利になった分、専門知識が必要になった。全体を直せる人が1〜2人しかいない「属人化」を、エージェントと人の両方で解消する。

1. **運用の手間を減らし、障害対応を速くする**：問い合わせへの一次回答や定期点検をエージェントが担う
2. **専門知識がなくても整備・運用できる**：エージェントが手順書を参照し、危険な操作は人の承認を挟んで実行する
3. **後世の鯖缶を育てる**：参加した学生がインフラの全体像を理解し、監修付きで保守作業ができるようになる

3つ目は1・2と同じくらい重要である。エージェントができても、それを直せる人がいなければ属人化は解消しない。

## 解決したい困りごと

| 困りごと | 誰が解決するか |
| --- | --- |
| 全体を把握している人が1〜2人しかいない。その人が卒業したら誰も直せない | エージェント＋次の鯖缶 |
| 鯖缶が不在だと対応が止まる | エージェント |
| 答えはドキュメントに書いてあるのに、質問者はどこを読めばいいか分からない | エージェント |
| 作業履歴を書くのが後回しになり、ドキュメントと実態がずれる | エージェントの作業レポート |
| 卒業のたびに引き継ぎが発生し、知識が失われる | 次の鯖缶を育てる |

## 鯖缶の仕事とエージェントの分担

| 仕事 | 内容 | 担当 |
| --- | --- | --- |
| Slack の問い合わせ対応 | 「つながらない」「使い方が分からない」に答える | エージェントが得意 |
| サーバー・サービスの追加 | Proxmox で LXC を作り、Cloudflare で外から見えるようにする | エージェントが得意（承認後に実行） |
| 定期点検 | ディスク残量、証明書の期限、バックアップ、更新待ちパッケージ | エージェントが得意 |
| 障害の原因調査と復旧 | ログを読み、状態を確認し、切り分けて直す | 人が必要（エージェントは補助） |
| 作業履歴を残す | 何を・なぜ・どうやったかをドキュメントに書く | 人が必要（エージェントは自分の作業レポートを残す） |
| 次の鯖缶への引き継ぎ | 卒業のたびに発生する | 人が必要 |

## 目指す姿

Slack の問い合わせを共通基盤が受け取り、2種類のエージェントに振り分ける。

```
Slack（問い合わせ、画像つき）
   │
   ▼
共通基盤 ── 受付・分類・振り分け（誰が、何を、画像の有無）
   │
   ├── ドキュメントで答えられる ──────────▶ ローカルLLM エージェント
   │                                         ドキュメントを検索し、引用つきで回答
   │                                         機密情報はここで伏せる
   │                                              │ 自分では無理と判断したら引き継ぐ
   │                                              ▼
   └── サーバーの調査・操作が必要 ────────▶ Claude エージェント
                                             調査 → 提案 → 承認 → 実行 → 作業レポート
   │
   ▼
元のスレッドに返信（必要なら追加の質問）
```

| 部品 | 章 | 担当 |
| --- | --- | --- |
| 共通基盤 | [10-common](../10-common/) | コース C |
| ローカルLLM エージェント | [20-local-llm](../20-local-llm/) | コース A |
| Claude エージェント | [30-claude-agent](../30-claude-agent/) | コース B |

## 2種類のエージェント

| 観点 | ローカルLLM エージェント | Claude エージェント |
| --- | --- | --- |
| モデル | 研究室の GPU サーバーで動かす公開モデル（Qwen、Gemma、gpt-oss など） | Claude など、API で呼ぶ最先端モデル |
| 主な仕事 | ドキュメントに基づく回答。外部に送る前の機密情報の処理（マスキング・一時トークン化） | サーバーの調査・操作、Cloudflare・Proxmox の設定変更、最新情報の収集、複数ログの突き合わせ |
| データ | 学内から出ない | Anthropic に送信する（学習には使われない設定。それでも機密は送らない） |
| 費用 | GPU の初期費用と電気代 | 使った分だけ課金 |

分ける理由は3つある。

1. **コスト**：問い合わせの大半はドキュメントで答えられる。毎回 API に投げると費用が膨らむ
2. **データの所在**：ログ・パスワード・個人情報は外に出せない。出すときも必ず伏せてから
3. **学習**：役割の違うエージェントが協調するマルチエージェント構成を、体系的に学びながら作る

## 自動化レベル（どこまで任せるか）

作業ごとに自動化レベルを決める。最初は「提案のみ」で動かし、提案が正しいかを人が確かめ、信頼できたものから順にレベルを上げる。

| レベル | 内容 | 例 |
| --- | --- | --- |
| 1：提案のみ | 調べて報告するだけ。人が確認してから返す | 障害の一次調査、ドキュメントに基づく回答（最初はここから） |
| 2：承認後に実行 | 担当者が Slack で承認したら実行する | サービス再起動、LXC の作成、Cloudflare の設定変更 |
| 3：自動実行 | 許可リスト内の読み取り操作だけ、無承認で実行する | 毎朝のヘルスチェック、精度が確認できた後のドキュメント回答 |

**当面やらせないこと**：アカウント・権限の変更、データの削除、ファイアウォールや Cloudflare の根幹設定の変更、承認なしの本番変更、外部への自動送信。

## 権限レベル（人にもエージェントにも同じ区分）

| レベル | 内容 | 誰が |
| --- | --- | --- |
| L0 | 閲覧（状態確認、ログ参照） | 全員 |
| L1 | 安全な操作（サービス再起動など、許可リスト内） | 監修付きで学生 |
| L2 | 作成・設定変更（LXC の作成、Cloudflare のアプリ追加） | 承認を得て、監修付きで学生 |
| L3 | 削除、ファイアウォール、sshd、経路、Cloudflare の根幹、エージェント自身 | Sage のみ（当面） |

本番の作業ルールは [project/process.md](../../project/process.md#本番サーバーでの作業) にある。
