# Issue・PR の運用ガイド

## どのテンプレートを使うか

| こんなとき | テンプレート | 行き先 |
|---|---|---|
| 「こんなことやらせたい」 | 💡 アイデア | 採用されたら docs/use-cases やタスクへ |
| 「A と B どっちにする？」 | 🧭 設計判断 | 決まったら `docs/adr/` に ADR を作成 |
| 「これってどういうこと？」 | ❓ 質問 | 回答がドキュメントに書くべき内容なら追記 |
| 具体的な作業 | ✅ タスク | マイルストーン（Phase）に紐づけ |
| エージェントがおかしな動きをした | 🐞 不具合 | 深刻度 S1/S2 は最優先 |
| 実際の障害と対応の記録 | 🔥 障害事例 | 将来の知識ベース・手順書の材料 |

## Issue の流れ

```
アイデア ──→ 議論 ──→ 設計判断(decision) ──→ ADR ──→ タスク ──→ PR
   │                                                     ↑
   └── 小さいものは直接タスク化 ─────────────────────────┘
```

1. 新しい Issue には自動で `status:triage` が付く
2. 整理するときに `area:*` と（必要なら）`risk:*` ラベルを付ける
3. 議論が必要なら `status:discussion`、決まったら `status:decided`
4. 設計判断は ADR に残してから Issue を閉じる（ADR に Issue 番号を書く）

## ラベル体系

ラベル定義は [`.github/labels.yml`](../.github/labels.yml) にまとめてある。

- `type:*` — Issue の種類（テンプレートで自動付与）
- `area:*` — 関係する領域
- `risk:*` — その機能が必要とする権限レベル（[safety.md](safety.md) の分類に対応）
- `status:*` — 進行状況

`risk:*` を付けておくと、「承認フローが必要な機能」を一覧しやすくなる。

## マイルストーン

[roadmap.md](roadmap.md) のフェーズをそのままマイルストーンにする。

- Phase 0: 構想整理
- Phase 1: 観察者（読み取り専用）
- Phase 2: 助言者（提案まで）
- Phase 3: 実行者（承認制）
- Phase 4: 自律運用

## 共有時の注意（重要）

サーバー運用の話なので、Issue に機密情報が混ざりやすい。投稿前に以下を伏せる。

- IP アドレス・ホスト名・ドメイン
- ユーザー名・メールアドレス
- API キー・トークン・パスワード
- 社内/学内ネットワーク構成がわかる情報

例：`192.168.1.10` → `<SERVER_A_IP>`、`gpu-node01` → `<HOST_A>`

## ラベル・マイルストーンの一括登録

GitHub にリポジトリを作ったあと、`gh` コマンドで登録できる（スクリプト化は後日）。

```sh
# ラベル例
gh label create "type:idea" --color a2eeef --description "アイデア・機能提案"

# マイルストーン例
gh api repos/OWNER/server-ai-agent/milestones -f title="Phase 0: 構想整理"
```
