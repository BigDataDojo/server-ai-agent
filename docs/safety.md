# 安全設計：権限・承認・監査・ロールバック

サーバーに root 権限で触れる AI は、便利さと同じだけ危険でもある。
「間違えても取り返しがつく」構成を最優先にする。

## 原則
1. **最小権限**：専用ユーザーで動かし、必要なコマンドだけ sudo で許可する
2. **許可リスト方式**：任意のシェルは渡さず、定義済みのツール/コマンドのみ実行可能にする
3. **読み取りと書き込みの分離**：読み取りは自由、変更は承認制
4. **人間の承認**：破壊的・不可逆な操作は必ず承認を挟む
5. **すべて記録**：入力・判断・実行・結果を監査ログへ
6. **ロールバック前提**：変更前にスナップショット / バックアップを取る

## 操作の分類（案）
| 分類 | 例 | 扱い |
|---|---|---|
| 参照 | `df`, `systemctl status`, ログ閲覧 | 自動実行可 |
| 軽微な変更 | ログローテーション、キャッシュ削除 | 設定次第で自動 |
| 変更 | パッケージ更新、設定ファイル変更、サービス再起動 | 承認必須 |
| 危険 | 再起動、カーネル更新、ファイル削除、ファイアウォール変更 | 承認必須 + 退避手順必須 |
| 禁止 | ディスクのフォーマット、ユーザー削除 等 | エージェントには実行させない |

## 想定リスクと対策
- **プロンプトインジェクション**：ログやファイル内容に仕込まれた指示に従ってしまう
  → 外部由来のテキストは「データ」として扱い、指示としては解釈しない設計にする
- **ハルシネーション**：存在しないオプションや誤った手順を実行する
  → dry-run、コマンドの事前検証、実行前に計画を提示
- **情報漏えい**：API へ機密情報を送ってしまう
  → マスキング層、機密処理はローカルモデル限定
- **暴走・ループ**：同じ操作を繰り返す
  → 実行回数・時間・コストの上限、キルスイッチ
